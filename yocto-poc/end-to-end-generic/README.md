# Generic Yocto chunked bootc build

This folder is a standalone, generic version of the project's end-to-end
Yocto proof of concept. It keeps image construction inside BitBake: the image
rootfs layout, OCI image, chunked image, encapsulated base, and bootc hybrid
are all generated by Yocto tasks.

The example build targets `qemuarm64` and produces:

```text
generic-chunked-bootc-image.oci
generic-chunked-bootc-image-chunked.oci
generic-chunked-bootc-image-base.oci
generic-chunked-bootc-image-hybrid.oci
```

## Build

The build is normally run in the project's prepared Lima VM:

```bash
cd yocto-poc/end-to-end-generic
scripts/vm-sync.sh
scripts/vm-kas.sh build end-to-end-generic/kas/chunked-bootc-qemuarm64.yaml
```

The synchronization script is orchestration only. The artifact build is owned
by the `meta-chunked-bootc` Yocto layer.

The generic wrapper uses an isolated `~/yocto/kas-work-generic` directory by
default, so it cannot consume stale sysroot or sstate state from the older
project-specific PoC. Override it with `CHUNKED_KAS_WORK_DIR` when needed.

Required host tools are `buildah`, `chunkah`, `ostree`, `ostree-encap`, and
`skopeo`.
They must be on the BitBake task PATH or added through `HOSTTOOLS`. Their
locations can be overridden in the KAS configuration:

```bitbake
CHUNKED_BOOTC_BUILDAH = "/opt/tools/buildah"
CHUNKED_BOOTC_CHUNKAH = "/opt/tools/chunkah"
CHUNKED_BOOTC_OSTREE = "/usr/bin/ostree"
CHUNKED_BOOTC_OSTREE_ENCAP = "/opt/tools/ostree-encap"
```

The example QEMU manifest sets `CHUNKED_BOOTC_OSTREE_ENCAP` explicitly to
`/usr/bin/ostree-encap` because BitBake tasks use a sanitized `HOSTTOOLS`
directory and should not depend on its symlink resolution order.

For registry-based upgrades, the target image also needs a target-architecture
`skopeo` available at `/usr/bin/skopeo`. Set `CHUNKED_BOOTC_SKOPEO_STATIC` to
the path of a static binary when the target distribution does not provide a
native package. It is intentionally empty by default; the example manifest
does not contain a host-specific binary path. Without this option, artifact
generation and initial installation still work, but an in-guest `bootc switch`
cannot pull from a registry.

## Configuration

The reusable classes support these main variables:

```bitbake
CHUNKED_BOOTC_VERSION = "v2"
CHUNKED_BOOTC_MAX_LAYERS = "32"
CHUNKED_BOOTC_HYBRID = "1"
CHUNKED_BOOTC_TITLE = "Generic bootc"
CHUNKED_BOOTC_KARGS = "root=/dev/vda rw"
  CHUNKED_BOOTC_VERSION_FILE = "chunked-bootc-version"
  CHUNKED_BOOTC_SKOPEO_STATIC = "/path/to/static/target-skopeo"
  CHUNKED_BOOTC_BASE_SYMLINKS = "..."
CHUNKED_BOOTC_BASE_MOUNTPOINTS = "dev proc sys boot run tmp"
```

An application image can inherit `chunked-bootc` and enable the artifact
classes without using the example image recipe.

## Validation

Runtime validation scripts are separate from artifact generation. They install
an already-generated hybrid image, boot it under QEMU, and inspect `bootc
status`; they do not edit the rootfs or OCI layout.

The upgrade helpers accept `CHUNKED_BOOTC_DISK` and
`CHUNKED_BOOTC_REGISTRY`. The interrupted-upgrade helper additionally accepts
`CHUNKED_BOOTC_INTERRUPT_DELAY` to control when its SIGKILL is injected.

The first validation milestone is the build-level check:

```bash
bitbake -e generic-chunked-bootc-image | grep -E '^(CHUNKED_BOOTC|IMAGE_CLASSES|IMAGE_FSTYPES)='
bitbake generic-chunked-bootc-image
```

Firmware/bootloader boot is a separate optional milestone. Direct-kernel QEMU
boot remains the fast PoC path until bootupd/GRUB is enabled in the image.

## Scope

This folder deliberately excludes ROS, Gazebo, Hummingbird application
recipes, and project-specific verification. Those can be added by an
application layer while reusing the generic classes.
